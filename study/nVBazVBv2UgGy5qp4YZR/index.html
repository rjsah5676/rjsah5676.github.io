캐시, 쿠키, 세션, 웹 스토리지: 이름은 비슷한데 저장 위치와 목적이 다르다

Network2026-2-17 21:23

"세션 스토리지에 넣었어요", "세션 만료됐어요", "캐시 지우고 다시 해보세요". 웹에서 무언가를 저장한다는 말은 많은데, 각각 어디에 저장되고, 누가 읽고, 언제 사라지는지가 다르다. 그 기준으로 정리한다.

한눈에

  1. HTTP 캐시: 브라우저(또는 CDN·프록시)가 응답 자체를 저장. 목적은 같은 요청을 다시 안 보내는 것.
  2. 쿠키: 브라우저에 저장되고, 조건이 맞으면 요청마다 자동으로 서버에 전송되는 작은 값.
  3. 서버 세션: 서버(메모리·Redis·DB)에 저장된 사용자 상태. 브라우저는 세션 ID만 쿠키로 들고 있다.
  4. localStorage / sessionStorage: 브라우저에만 있는 키-값 저장소. 서버로 자동 전송되지 않는다. 이름에 세션이 들어가도 서버 세션과는 무관하다.

HTTP 캐시

서버가 응답 헤더로 "얼마나, 어떻게 재사용해도 되는지" 알려준다.

Cache-Control: public, max-age=31536000, immutable # 해시가 붙은 JS/CSS
Cache-Control: no-cache # HTML: 쓰기 전에 항상 재검증
Cache-Control: no-store # 개인정보: 아예 저장 금지
  1. max-age: 이 시간 동안은 서버에 묻지도 않고 캐시를 쓴다(fresh).
  2. no-cache: 저장은 하되 쓰기 전에 매번 서버에 확인하라는 뜻이다. 저장하지 말라는 건 no-store다. 이름 때문에 가장 많이 헷갈린다.
  3. 재검증: 캐시가 오래됐으면 If-None-Match: "etag값"을 보내고, 서버는 바뀐 게 없으면 본문 없이 304 Not Modified를 준다. 전송량이 확 준다.

배포 전략은 보통 이렇게 간다. 파일명에 내용 해시가 붙은 정적 자산(app.3f9a1c.js)은 1년 + immutable로 두고, 그걸 가리키는 HTML은 no-cache로 둔다. 배포하면 HTML만 새로 받고, 바뀐 JS는 파일명이 달라서 자연스럽게 새로 받는다. "캐시 지우고 해보세요"가 필요하다면 이 규칙 중 하나가 깨져 있는 것이다.

쿠키

Set-Cookie: SESSION=abc123; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=1800
  1. HttpOnly: JS(document.cookie)로 읽을 수 없다. XSS로 스크립트가 주입돼도 세션 ID를 훔쳐가지 못한다.
  2. Secure: HTTPS에서만 전송.
  3. SameSite: 다른 사이트에서 시작된 요청에 쿠키를 붙일지. Strict는 안 붙임, Lax는 링크 클릭 같은 최상위 GET 이동에만 붙임, None은 항상(Secure 필수). Chrome은 지정하지 않으면 Lax로 취급한다. CSRF 방어의 1차 방어선이다.
  4. Max-Age/Expires가 없으면 브라우저를 닫을 때 지워지는 세션 쿠키가 된다.
  5. Domain, Path: 어느 주소로 요청할 때 보낼지.

쿠키는 요청마다 따라가므로 크면 모든 요청이 무거워진다(도메인당 대략 4KB 제한). 큰 데이터를 넣는 곳이 아니다.

서버 세션

로그인하면 서버가 사용자 정보를 세션 저장소에 넣고, 그 키(세션 ID)만 쿠키로 내려준다. 톰캣의 JSESSIONID가 대표적이다.

  1. 장점: 민감한 정보가 브라우저에 없다. 서버에서 세션을 지우면 즉시 로그아웃된다.
  2. 단점: 서버가 상태를 가진다. 서버가 여러 대면 A 서버에서 로그인한 세션을 B 서버가 모른다.

서버를 늘릴 때 해결책은 보통 둘이다.

  1. Sticky session: 로드밸런서가 같은 사용자를 같은 서버로 보낸다. 간단하지만 그 서버가 죽으면 세션도 날아간다.
  2. 세션 저장소 분리: Spring Session + Redis처럼 세션을 공용 저장소에 둔다. 서버는 무상태가 되고 몇 대든 늘릴 수 있다.

토큰(JWT)은 어디에 해당하나

JWT는 사용자 정보와 서명을 토큰 자체에 담아서, 서버가 저장소를 조회하지 않고 서명만 검증한다. 서버 확장은 쉽지만 발급한 토큰을 만료 전에 무효화하기 어렵다. 그래서 짧은 수명의 access token + 서버에서 관리하는 refresh token 조합을 많이 쓴다. 저장 위치는 XSS를 생각하면 localStorage보다 HttpOnly 쿠키가 안전하고, 그 경우 CSRF를 SameSite와 CSRF 토큰으로 막는다.

localStorage와 sessionStorage

  1. 둘 다 출처(origin)별로 수 MB 정도, 문자열만, 동기 API다.
  2. localStorage: 지우기 전까지 유지. 같은 출처의 모든 탭이 공유한다.
  3. sessionStorage: 탭 단위. 탭을 닫으면 사라지고, 같은 사이트라도 다른 탭과는 공유하지 않는다.
  4. JS로 읽을 수 있으니 XSS에 노출된다. 토큰이나 개인정보를 넣는 곳이 아니라 UI 설정(테마, 볼륨, 마지막 탭) 같은 값을 넣는 곳이다.
  5. SSR 환경에서는 서버에 없으니 렌더 중에 읽지 말고 마운트 후에 읽는다.

정리

  1. 재사용할 응답이면 HTTP 캐시, 서버가 매 요청 알아야 하는 작은 값이면 쿠키, 민감한 사용자 상태는 서버 세션(키만 쿠키로), 브라우저 혼자 쓰는 설정은 웹 스토리지.
  2. no-cache는 저장 금지가 아니다. 저장 금지는 no-store.
  3. 세션 ID 쿠키는 HttpOnly; Secure; SameSite를 기본으로 붙인다.
