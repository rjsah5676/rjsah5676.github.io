1초 전에 로그인한 사람인지 모른다. 그래서 "이 사용자가 누구인지" 같은 <strong>상태</strong>를 이어 붙이기 위해 쿠키와 세션이 생겼다. 반면 캐시는 상태와 관계없이, 이미 받은 응답을 재사용해서 <strong>성능</strong>을 높이려는 장치다.</p><h2>2. 한눈에 비교</h2><table><tbody><tr><td <code>Set-Cookie</code>로 내려주면 브라우저가 저장하고, 이후 같은 도메인으로 요청할 때 <code>Cookie</code> 헤더에 자동으로 실어 보낸다.</p><table><tbody><tr><td data-row="row-1"><strong>속성</strong></td><td data-row="row-1"><strong>의미</strong></td></tr><tr><td data-row="row-2">Expires / Max-Age</td><td data-row="row-2">만료 시점. 없으면 브라우저를 닫을 때 삭제되는 세션 쿠키</td></tr><tr><td data-row="row-3">Domain / Path</td><td data-row="row-3">어느 주소로 요청할 때 보낼지</td></tr><tr><td data-row="row-4">HttpOnly</td><td data-row="row-4">JS(document.cookie)로 읽기 금지 → XSS로 탈취 방지</td></tr><tr><td data-row="row-5">Secure</td><td data-row="row-5">HTTPS 요청에만 전송</td></tr><tr><td data-row="row-6">SameSite</td><td data-row="row-6">다른 사이트에서 시작된 요청에 보낼지 (Strict / Lax / None) → CSRF 방어</td></tr></tbody></table><ol><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><code>SameSite=Lax</code>는 다른 사이트에서 링크를 눌러 이동하는 GET에는 보내고, 다른 사이트의 폼 POST나 이미지·iframe 요청에는 보내지 않는다. Chrome은 지정하지 않으면 Lax로 취급한다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><code>SameSite=None</code>은 항상 보내며, 반드시 <code>Secure</code>와 함께 써야 한다.</li></ol><h2>4. 세션 (Session)</h2><p>사용자 정보는 서버에 저장하고, 브라우저에는 그 정보를 찾을 수 있는 <strong>세션 ID</strong>만 쿠키로 준다.</p><ol><li data-list="ordered"><span class="ql-ui" contenteditable="false"></span>로그인 성공 → 서버가 세션 저장소에 <code>{세션ID: 사용자정보}</code> 저장</li><li data-list="ordered"><span class="ql-ui" contenteditable="false"></span>응답으로 <code>Set-Cookie: JSESSIONID=abc123; HttpOnly</code></li><li data-list="ordered"><span class="ql-ui" contenteditable="false"></span>이후 요청마다 브라우저가 <code>Cookie: JSESSIONID=abc123</code> 전송</li><li data-list="ordered"><span class="ql-ui" contenteditable="false"></span>서버는 세션 ID로 저장소를 조회해 사용자를 식별</li></ol><p>쿠키만 쓰면 <code>userId=42</code>를 사용자가 <code>43</code>으로 바꿔 보낼 수 있다. 세션은 의미 없는 난수 ID만 주고 진짜 정보는 서버에 있으니 변조할 수 없다. 대신 세션 ID 자체를 훔치면(세션 하이재킹) 그 사용자로 행세할 수 있어서 <code>HttpOnly</code>, <code>Secure</code>, 로그인 시 세션 ID 재발급(세션 고정 공격 방지)이 필요하다.</p><p><strong>서버가 여러 대일 때의 문제</strong>: A 서버에서 만든 세션을 B 서버는 모른다.</p><table><tbody><tr><td data-row="row-1"><strong>방법</strong></td><td data-row="row-1"><strong>설명</strong></td><td data-row="row-1"><strong>단점</strong></td></tr><tr><td data-row="row-2">Sticky Session</td><td data-row="row-2">로드밸런서가 같은 사용자를 같은 서버로 보냄</td><td 쓴다.</p><h2>5. 캐시 (HTTP Cache)</h2><p>서버가 응답 헤더로 "이 응답을 얼마나, 어떻게 재사용해도 되는지" 알려준다.</p><table><tbody><tr><td data-row="row-1"><strong>헤더 값</strong></td><td contenteditable="false"></span>첫 응답: <code>ETag: "v1"</code> (또는 <code>Last-Modified</code>)</li><li data-list="ordered"><span class="ql-ui" contenteditable="false"></span>만료 후 요청: <code>If-None-Match: "v1"</code></li><li data-list="ordered"><span class="ql-ui" contenteditable="false"></span>안 바뀌었으면 <code>304 Not Modified</code> (본문 없음) → 캐시 재사용</li><li data-list="ordered"><span data-row="row-6">가능</td><td data-row="row-6">가능</td></tr></tbody></table><p>sessionStorage는 이름만 세션일 뿐 서버 세션과 아무 관계가 없다. 모두 JS로 읽을 수 있어 XSS에 노출되므로 토큰·개인정보보다 UI 설정 저장에 적합하다.</p><h2>7. 함께 묻는 것: 세션 vs Token</td></tr></tbody></table><h2>8. 실제로 어떻게 적용되나</h2><ol><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>로그인 유지</strong>: 세션 방식이면 세션 ID 쿠키에 <code>HttpOnly; Secure; SameSite=Lax</code>를 붙인다. 쿠키는 운반 수단, 세션은 실제 정보 저장소로 두 개념이 같이 쓰이는 대표 사례다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>"오늘 하루 보지 않기" 팝업</strong>: 서버가 알 필요 없는 UI 상태라 쿠키나 localStorage에 만료일과 함께 저장한다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>정적 파일 배포</strong>: <code>app.3f9a1c.js</code>처럼 내용 해시가 붙은 파일은 <code>max-age=31536000, immutable</code>, 그 파일을 가리키는 HTML은 <code>no-cache</code>. 배포하면 HTML만 재검증되고 바뀐 JS는 파일명이 달라 새로 받는다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>마이페이지 API 응답</strong>: 사용자별 데이터는 <code>private</code> 또는 <code>no-store</code>로 CDN에 저장되지 않게 한다. 안 그러면 다른 사람에게 내 정보가 캐시로 나갈 수 있다.</li></ol><h2>9. 자주 헷갈리는 포인트</h2><ol><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><code>no-cache</code>는 "캐시 금지"가 아니라 "매번 확인 후 사용"이다. 금지는 <code>no-store</code>.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span>세션도 결국 쿠키를 쓴다. 차이는 쿠키에 정보 자체를 넣느냐, 정보를 찾을 키만 넣느냐다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span>쿠키는 요청마다 따라가므로 많이 넣으면 모든 요청이 무거워진다.</li></ol><h2>10. 면접 질문으로 정리</h2><ol><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>Q. 쿠키와 세션의 차이는?</strong> 쿠키는 클라이언트에 저장되어 요청마다 서버로 전송되는 데이터이고, 세션은 서버에 저장되는 사용자 상태다. 세션은 식별용 세션 ID만 쿠키로 주고받아 보안상 유리하지만 서버 자원을 쓰고, 서버가 여러 대면 세션 공유가 필요하다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>Q. 캐시는 쿠키·세션과 무엇이 다른가?</strong> 쿠키·세션은 상태 유지가 목적이고, 캐시는 이미 받은 응답을 재사용해 응답 속도와 트래픽을 줄이는 게 목적이다. Cache-Control, ETag 같은 HTTP 헤더로 제어한다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>Q. no-cache와 no-store의 차이는?</strong> no-cache는 저장하되 쓰기 전에 서버에 재검증하고, no-store는 아예 저장하지 않는다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>Q. 쿠키를 안전하게 쓰려면?</strong> HttpOnly로 JS 접근을 막고, Secure로 HTTPS에서만 보내고, SameSite로 다른 사이트 요청에 실리지 않게 해 CSRF를 막는다.</li></ol>9:X
