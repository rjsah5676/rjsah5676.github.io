SSR은 왜 필요한가: CSR과의 차이를 렌더링 타임라인으로 보기

Next/Express2026-4-14 22:05

"SEO 때문에 SSR을 쓴다"는 말은 맞지만 절반만 맞다. SSR과 CSR의 차이는 누가, 언제 HTML을 만드느냐이고, 그 차이가 첫 화면 속도, 검색 노출, 서버 비용, 개발 방식까지 바꾼다.

CSR: 브라우저가 HTML을 만든다

  1. 서버는 거의 빈 HTML(<div id="root"></div>)과 JS 번들 링크를 준다.
  2. 브라우저가 JS를 내려받아 실행한다.
  3. JS가 API를 호출하고, 데이터를 받아 DOM을 그린다.

사용자는 3번이 끝날 때까지 흰 화면이나 로딩 스피너를 본다. 번들이 크고 기기가 느릴수록 길어진다. 대신 한 번 뜨면 페이지 이동은 JS가 처리해서 빠르고, 서버는 정적 파일만 주면 되니 CDN에 올리기 쉽다.

SSR: 서버가 요청마다 HTML을 만든다

  1. 요청이 오면 서버가 데이터를 조회하고 컴포넌트를 렌더해서 완성된 HTML을 보낸다.
  2. 브라우저는 JS 실행 전에 내용을 바로 그린다(FCP/LCP가 빨라짐).
  3. JS가 도착하면 이미 있는 DOM에 이벤트 핸들러를 붙인다(hydration). 이때부터 버튼이 동작한다.

HTML이 보이는 시점과 상호작용 가능한 시점이 다르다는 게 핵심이다. 내용은 빨리 보이지만, hydration 전에 누른 버튼은 반응하지 않을 수 있다.

대표 차이

  1. 첫 화면: CSR은 JS 다운로드·실행·API 응답을 다 기다린다. SSR은 HTML에 내용이 들어있다.
  2. SEO·공유 미리보기: 구글은 JS를 실행해서 색인하긴 하지만 렌더링 대기열을 거쳐 늦어질 수 있고, 카카오톡·슬랙 같은 링크 미리보기 봇은 대부분 JS를 실행하지 않는다. og: 메타 태그가 HTML에 있어야 한다.
  3. TTFB: SSR은 서버가 데이터를 조회하고 렌더하는 시간만큼 첫 바이트가 늦다. 느린 API 하나가 페이지 전체를 붙잡는다(스트리밍으로 완화).
  4. 서버 비용: CSR은 정적 파일이라 CDN이면 끝. SSR은 요청마다 연산이 필요하다.
  5. 개발 제약: SSR 코드는 서버에서도 실행돼서 window, localStorage를 렌더 중에 쓰면 터진다. 서버 HTML과 클라이언트 첫 렌더가 다르면 hydration mismatch가 난다.

hydration mismatch를 피하는 법

// 나쁜 예: 서버(UTC)와 브라우저(KST)의 결과가 다름
<span>{new Date().toLocaleTimeString()}</span>

// 좋은 예: 첫 렌더는 서버와 똑같이, 브라우저 전용 값은 마운트 후에
const [now, setNow] = useState(null);
useEffect(() => setNow(new Date()), []);
<span>{now ? now.toLocaleTimeString() : ""}</span>

날짜, 랜덤 값, window.innerWidth, localStorage 값이 대표적인 원인이다. 이 사이트의 지뢰찾기도 화면 방향을 useState(window.innerHeight > ...)로 초기화했다가 정적 빌드에서 크래시가 나서 마운트 후 갱신으로 바꿨다.

SSR만 있는 게 아니다: SSG, ISR

  1. SSG: 빌드할 때 HTML을 미리 만든다. 블로그 글처럼 요청마다 달라지지 않는 페이지에 가장 빠르고 싸다. 이 사이트는 output: "export"로 전부 SSG다.
  2. ISR: SSG 결과를 일정 시간마다 백그라운드에서 다시 만든다. 서버(또는 Vercel 같은 플랫폼)가 필요하다.
  3. SSR: 요청마다 달라야 하는 페이지(로그인 사용자별 화면, 실시간 재고·가격).

페이지마다 고를 수 있다는 게 Next.js의 장점이다. 공개 페이지는 SSG로, 마이페이지는 CSR이나 SSR로.

Next.js App Router에서는

App Router의 컴포넌트는 기본이 Server Component다. 서버에서만 실행되고, JS 번들에 포함되지 않는다. 상태나 이벤트가 필요한 부분만 "use client"로 표시하면 그 부분만 hydration된다.

// app/products/[id]/page.tsx (Server Component)
export default async function Page({ params }) {
const { id } = await params;
const product = await getProduct(id); // DB/API를 서버에서 직접
return (
<>
<h1>{product.name}</h1> {/* HTML로만 나감 */}
<AddToCartButton id={product.id} /> {/* "use client" 컴포넌트만 JS 포함 */}
</>
);
}

"SSR이냐 CSR이냐"가 페이지 단위에서 컴포넌트 단위로 내려온 셈이다. 데이터는 서버에서 가져와 HTML로 보내고, 상호작용이 필요한 작은 섬만 클라이언트에서 돌린다.

언제 무엇을

  1. 검색 노출, 링크 미리보기, 첫 화면 속도가 중요한 공개 페이지: SSG 또는 SSR
  2. 로그인 뒤 관리자 화면, 대시보드처럼 SEO가 필요 없고 상호작용이 많은 화면: CSR로 충분
  3. 내용이 자주 안 바뀌면 SSR보다 SSG(+재배포/ISR)가 싸고 빠르다

결국 기준은 "이 HTML을 언제 만들어 둘 수 있나"다. 빌드 때 만들 수 있으면 SSG, 요청이 와야 알 수 있으면 SSR, 사용자의 브라우저에서만 알 수 있으면 CSR이다.
