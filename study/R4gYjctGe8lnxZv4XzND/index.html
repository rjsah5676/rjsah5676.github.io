인덱스는 왜 빠르고, 왜 안 탈 때가 있나 (B-Tree와 복합 인덱스)

Database2025-12-9 22:27

"인덱스 걸면 빨라진다"까지는 다 안다. 그런데 인덱스를 걸었는데도 느린 쿼리, 인덱스가 있는데 옵티마이저가 안 쓰는 쿼리가 계속 나온다. InnoDB(MySQL/MariaDB) 기준으로 인덱스가 어떻게 생겼는지부터 보면 대부분 설명된다.

B-Tree 인덱스는 정렬된 목차다

인덱스는 컬럼 값을 정렬된 상태로 저장한 B+Tree다. 루트 → 브랜치 → 리프로 내려가며 찾으니, 백만 건이어도 몇 단계 만에 원하는 위치를 찾는다. 리프 노드끼리는 연결돼 있어서 범위 조회(BETWEEN, >)도 시작점을 찾은 뒤 옆으로 읽으면 된다.

클러스터드 인덱스와 세컨더리 인덱스

  1. InnoDB의 테이블 데이터 자체가 PK 순서로 정렬된 B+Tree다(클러스터드 인덱스).
  2. 다른 인덱스(세컨더리)의 리프에는 행 위치가 아니라 PK 값이 들어 있다.
  3. 그래서 세컨더리 인덱스로 찾으면: 인덱스에서 PK를 얻고 → PK 인덱스를 한 번 더 탄다.

여기서 두 가지가 나온다. PK가 크면(UUID 문자열 등) 모든 인덱스가 같이 커진다. 그리고 인덱스로 찾은 행이 아주 많으면 "PK로 다시 찾아가기"가 행 수만큼 반복돼서 차라리 테이블 전체를 읽는 게 빠를 수 있다. 옵티마이저가 인덱스를 무시하는 대표적인 이유다.

복합 인덱스는 왼쪽부터

INDEX (member_id, status, ordered_at)은 전화번호부처럼 member_id로 먼저 정렬하고, 같으면 status, 같으면 ordered_at으로 정렬한 것이다.

  1. WHERE member_id = ? → 사용 가능
  2. WHERE member_id = ? AND status = ? → 사용 가능
  3. WHERE status = ? → 첫 컬럼이 없어서 범위를 좁힐 수 없음
  4. WHERE member_id = ? AND ordered_at > ? → member_id까지만 좁히고 status를 건너뛰어 ordered_at은 걸러내는 데만 씀

범위 조건 뒤의 컬럼은 정렬 순서를 이용하지 못한다. 그래서 보통 = 조건 컬럼을 앞에, 범위 조건 컬럼을 뒤에 둔다.

-- 회원의 최근 주문 목록: member_id(=) → ordered_at(정렬)
CREATE INDEX idx_orders_member_date ON orders (member_id, ordered_at);

SELECT order_id, ordered_at
FROM orders
WHERE member_id = 42
ORDER BY ordered_at DESC
LIMIT 20; -- 인덱스 순서대로 20개만 읽고 끝 (filesort 없음)

커버링 인덱스

조회하는 컬럼이 전부 인덱스 안에 있으면 테이블(PK 인덱스)까지 가지 않는다. 위 쿼리는 order_id가 PK라 세컨더리 인덱스 리프에 이미 있고, member_id, ordered_at도 인덱스에 있으니 인덱스만 읽고 끝난다. EXPLAIN의 Extra에 Using index가 보이면 커버링이다. SELECT *가 커버링을 깨는 흔한 원인이다.

인덱스를 못 타게 만드는 습관

WHERE DATE(ordered_at) = '2025-12-09' -- 컬럼을 함수로 감쌈
WHERE ordered_at >= '2025-12-09' AND ordered_at < '2025-12-10' -- 이렇게

WHERE phone = 01012345678 -- 문자열 컬럼에 숫자 비교 → 형변환
WHERE phone = '01012345678' -- 타입 맞추기

WHERE name LIKE '%고기' -- 앞이 와일드카드면 정렬을 못 씀
WHERE name LIKE '고기%' -- 앞부분 고정은 범위 검색 가능

WHERE member_id = ? OR status = ? -- OR은 각각 인덱스가 없으면 풀스캔

인덱스는 "정렬된 원래 값"이다. 컬럼 값을 가공하는 순간 정렬 순서와 맞지 않으니 쓸 수 없다고 생각하면 기억하기 쉽다.

카디널리티와 선택도

gender, deleted_yn처럼 값 종류가 적은 컬럼 단독 인덱스는 거의 효과가 없다. 걸러내도 절반이 남으면 PK로 다시 찾아가는 비용이 더 크다. 다만 복합 인덱스의 일부로는 의미가 있다(= 조건으로 쓰일 때).

인덱스의 비용

  1. INSERT/UPDATE/DELETE 때마다 모든 인덱스를 같이 고쳐야 한다. 쓰기가 많은 테이블에 인덱스가 10개면 쓰기가 그만큼 느려진다.
  2. 비슷한 인덱스((a)와 (a, b))는 앞쪽이 중복이다. (a, b)가 a 단독 조건도 처리한다.

EXPLAIN에서 볼 것

  1. type: const, eq_ref, ref, range는 좋음. index(인덱스 전체 스캔), ALL(테이블 풀스캔)은 의심.
  2. key: 실제로 고른 인덱스. possible_keys에 있는데 key가 NULL이면 옵티마이저가 버린 것.
  3. rows: 읽을 것으로 예상한 행 수.
  4. Extra: Using index(커버링, 좋음), Using filesort, Using temporary(정렬·그룹핑을 따로 함, 큰 결과면 느림).

정리

  1. 인덱스는 정렬된 값이다. 값을 가공하거나 타입이 다르면 못 쓴다.
  2. 복합 인덱스는 왼쪽부터, = 컬럼 먼저, 범위·정렬 컬럼 나중.
  3. 많이 조회하는 쿼리는 커버링을 노린다. SELECT *는 피한다.
  4. 인덱스를 추가하기 전후로 꼭 EXPLAIN을 본다.
