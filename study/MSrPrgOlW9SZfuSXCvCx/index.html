@Transactional이 동작하지 않는 경우들: 프록시와 롤백 규칙

Backend2026-7-14 21:58

@Transactional은 애노테이션 하나로 트랜잭션을 걸어주지만, 붙였는데 롤백이 안 되거나, 안 붙인 곳까지 롤백되는 일이 생긴다. 원인은 거의 항상 두 가지다. 프록시를 거쳤는가, 그리고 어떤 예외가 롤백을 일으키는가.

동작 원리: 프록시가 감싼다

스프링은 @Transactional이 있는 빈 대신 프록시를 주입한다. 프록시는 대략 이런 일을 한다.

// 개념적인 프록시
public Order placeOrder(Request req) {
TransactionStatus tx = txManager.getTransaction(definition);
try {
Order result = target.placeOrder(req); // 진짜 객체 호출
txManager.commit(tx);
return result;
} catch (RuntimeException | Error e) {
txManager.rollback(tx);
throw e;
}
}

트랜잭션은 프록시를 통해 들어올 때만 시작된다. 이걸 기억하면 아래 함정이 전부 설명된다.

함정 1: 같은 클래스 안에서 호출 (self-invocation)

@Service
public class OrderService {
public void placeAll(List<Request> reqs) {
for (Request r : reqs) {
placeOne(r); // this.placeOne → 프록시를 안 거침
}
}

@Transactional
public void placeOne(Request r) { ... } // 트랜잭션이 안 걸림
}

placeAll은 프록시를 통해 들어왔지만, 그 안에서 this.placeOne()은 진짜 객체의 메서드를 직접 부른다. 해결은 placeOne을 다른 빈으로 분리하는 것이 가장 깔끔하다. 자기 자신을 주입받거나 AopContext.currentProxy()를 쓰는 방법도 있지만 구조가 꼬인다.

함정 2: 메서드 접근 제어자

프록시가 가로챌 수 없는 메서드에는 적용되지 않는다. private 메서드는 당연히 안 되고, Spring 6 이전에는 public이 아닌 메서드도 무시됐다(6.0부터 클래스 기반 프록시에서 protected·package-private도 지원). 헷갈리면 public으로 둔다.

함정 3: 체크 예외는 기본적으로 롤백하지 않는다

기본 규칙은 **RuntimeException과 Error만 롤백**이다. IOException 같은 체크 예외는 커밋된다.

@Transactional(rollbackFor = Exception.class)
public void importFile(MultipartFile f) throws IOException { ... }

비즈니스 예외를 체크 예외로 만들어두고 롤백을 기대했다면 데이터가 반쯤 저장된다. 팀 규칙으로 비즈니스 예외는 RuntimeException을 상속하게 하거나, rollbackFor를 명시한다.

함정 4: 예외를 잡아버리면 커밋된다

@Transactional
public void pay(Order o) {
try {
orderMapper.updateStatus(o.getId(), PAID);
paymentClient.approve(o); // 여기서 예외
} catch (Exception e) {
log.error("결제 실패", e); // 삼킴 → 프록시는 정상 종료로 보고 커밋
}
}

상태는 PAID로 바뀌었는데 결제는 안 된 데이터가 남는다. 잡았다면 다시 던지거나, TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()로 롤백을 표시한다.

함정 5: 안쪽에서 잡았는데 바깥이 롤백된다 (UnexpectedRollbackException)

@Transactional
public void writeComment(Comment c) {
commentMapper.insert(c);
try {
pointService.giveFirstCommentPoint(c.getMemberId()); // @Transactional (REQUIRED)
} catch (Exception e) {
// 포인트 실패는 무시하고 댓글은 저장하고 싶음
}
}

REQUIRED(기본)는 기존 트랜잭션에 참여한다. 안쪽 메서드에서 런타임 예외가 나면 프록시가 공유 중인 트랜잭션 전체를 rollback-only로 표시한다. 바깥에서 예외를 잡아도 커밋 시점에 이미 롤백 표시가 있어서 UnexpectedRollbackException이 나고 댓글까지 롤백된다.

안쪽 작업을 독립시키려면 @Transactional(propagation = Propagation.REQUIRES_NEW)로 별도 트랜잭션을 연다. 단, 새 커넥션을 하나 더 쓰므로 바깥 트랜잭션이 잠근 행을 안쪽에서 수정하면 서로 기다리는 상황이 생길 수 있다. 또는 커밋 이후 이벤트(@TransactionalEventListener(phase = AFTER_COMMIT))로 아예 분리한다.

함정 6: 트랜잭션 안에서 외부 호출

트랜잭션이 열려 있는 동안 DB 커넥션을 붙잡는다. 그 안에서 외부 API가 3초 걸리면 커넥션도 3초 묶인다. 트래픽이 몰리면 커넥션 풀이 고갈된다. 외부 호출은 트랜잭션 밖으로 빼거나, DB 작업을 짧게 나눈다.

readOnly

@Transactional(readOnly = true)는 조회 전용임을 알려준다. JPA에서는 더티 체킹을 생략해 가벼워지고, 읽기 전용 복제 DB로 라우팅하는 설정의 기준으로도 쓴다. 쓰기를 막아주는 보안 장치로 기대하면 안 된다(드라이버·DB에 따라 다름).

정리

  1. 트랜잭션은 프록시를 통해 호출될 때만 시작된다. 같은 클래스 내부 호출은 무시된다.
  2. 기본 롤백은 런타임 예외와 Error. 체크 예외는 rollbackFor.
  3. 예외를 삼키면 커밋된다. 안쪽 REQUIRED 메서드의 예외는 잡아도 전체가 롤백된다.
  4. 독립적으로 커밋돼야 하는 작업은 REQUIRES_NEW나 커밋 후 이벤트로 분리한다.
