19:T2d9a,<blockquote><strong>IoC(제어의 역전)</strong>는 객체의 생성과 연결을 개발자가 아니라 프레임워크(컨테이너)가 맡는 것이고, <strong>DI(의존성 주입)</strong>는 그 IoC를 구현하는 방법으로, 객체가 필요한 의존성을 외부에서 넣어주는 것이다.</blockquote><h2>1. 의존성(Dependency)이란</h2><p>A가 동작하려면 B가 필요할 때 "A는 B에 의존한다"고 한다. <code>OrderService</code>가 결제를 위해 <code>PaymentClient</code>를 쓴다면 OrderService는 PaymentClient에 의존한다. 문제는 <strong>누가 B를 만들고 고르느냐</strong>다.</p><div class="ql-code-block-container" spellcheck="false"><div class="ql-code-block" data-language="plain">// A가 직접 B를 생성: 구현체 선택까지 A가 책임짐</div><div class="ql-code-block" data-language="plain">public class OrderService {</div><div class="ql-code-block" data-language="plain">    private final PaymentClient client = new TossPaymentClient();</div><div class="ql-code-block" data-language="plain">}</div><div class="ql-code-block" data-language="plain"><br></div><div class="ql-code-block" data-language="plain">// 외부에서 B를 받음: A는 역할(인터페이스)만 알면 됨</div><div class="ql-code-block" data-language="plain">public class OrderService {</div><div class="ql-code-block" data-language="plain">    private final PaymentClient client;</div><div class="ql-code-block" data-language="plain">    public OrderService(PaymentClient client) { this.client = client; }</div><div class="ql-code-block" data-language="plain">}</div></div><h2>2. 직접 생성 vs 주입</h2><table><tbody><tr><td data-row="row-1"><strong>구분</strong></td><td data-row="row-1"><strong>직접 생성 (new)</strong></td><td data-row="row-1"><strong>의존성 주입 (DI)</strong></td></tr><tr><td data-row="row-2">구현체 선택</td><td data-row="row-2">사용하는 클래스가 결정</td><td data-row="row-2">외부(컨테이너, 설정)가 결정</td></tr><tr><td data-row="row-3">결합도</td><td data-row="row-3">높음 (구현체에 묶임)</td><td data-row="row-3">낮음 (인터페이스에만 의존)</td></tr><tr><td data-row="row-4">구현 교체</td><td data-row="row-4">사용하는 쪽 코드 수정 필요</td><td data-row="row-4">설정만 변경</td></tr><tr><td data-row="row-5">테스트</td><td data-row="row-5">가짜 객체로 바꾸기 어려움</td><td data-row="row-5">생성자로 가짜 객체 전달 가능</td></tr><tr><td data-row="row-6">객체 수명 관리</td><td data-row="row-6">개발자가 직접</td><td data-row="row-6">컨테이너가 관리</td></tr></tbody></table><p>DI는 SOLID의 <strong>DIP(의존 역전 원칙)</strong>, "구체가 아니라 추상에 의존하라"를 실천하는 수단이기도 하다.</p><h2>3. IoC 컨테이너와 빈</h2><ol><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>IoC 컨테이너</strong>: 스프링에서는 <code>ApplicationContext</code>. 객체를 만들고, 의존성을 연결하고, 생명주기를 관리한다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>빈(Bean)</strong>: 컨테이너가 생성하고 관리하는 객체.</li></ol><table><tbody><tr><td data-row="row-1"><strong>등록 방법</strong></td><td 때</td></tr></tbody></table><p><code>@Service</code>, <code>@Repository</code>, <code>@Controller</code>는 모두 <code>@Component</code>의 특수화로, 역할을 드러내는 이름표다. <code>@Repository</code>는 DB 예외를 스프링 예외로 변환하는 (<code>@PostConstruct</code>)</li><li data-list="ordered"><span class="ql-ui" contenteditable="false"></span>사용</li><li data-list="ordered"><span class="ql-ui" contenteditable="false"></span>소멸 전 콜백 (<code>@PreDestroy</code>)</li><li data-list="ordered"><span class="ql-ui" contenteditable="false"></span>컨테이너 종료</li></ol><p>의존성은 3단계에서 들어오므로, 생성자 안에서는 생성자 주입으로 받은 것만 쓸 수 있고, 필드·수정자 주입 값은 때</h2><table><tbody><tr><td data-row="row-1"><strong>방법</strong></td><td data-row="row-1"><strong>설명</strong></td></tr><tr><td data-row="row-2">@Primary</td><td data-row="row-2">여러 후보 중 기본으로 쓸 빈 data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>결제 수단별 전략 패턴</strong>: <code>PaymentClient</code> 인터페이스의 구현(Toss, 카드사 등)을 <code>List&lt;PaymentClient&gt;</code>로 전부 주입받아 Map으로 만들어 두면, 결제 수단이 추가돼도 구현 클래스 하나만 추가하면 된다. "같은 타입의 빈 여러 개를 컬렉션으로 주입"을 활용한 것이다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>다중 DataSource</strong>: DB가 두 개면 같은 타입(<code>DataSource</code>)의 빈이 두 개가 된다. 하나에 <code>@Primary</code>를 붙이고 다른 쪽은 <code>@Qualifier</code>로 골라 쓴다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>테스트</strong>: 생성자 주입이면 <code>new OrderService(fakePaymentClient)</code>처럼 스프링 없이 가짜 객체로 유닛 테스트할 수 있다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>@Transactional과 프록시</strong>: 컨테이너는 원본 빈 대신 프록시를 주입할 수 있다. 트랜잭션, 캐시 같은 기능이 이 방식으로 붙는다. 그래서 같은 클래스 안에서 자기 메서드를 직접 호출하면 프록시를 거치지 않아 <code>@Transactional</code>이 적용되지 않는다.</li></ol><h2>9. 순환 참조</h2><p>A가 B를, B가 A를 생성자로 받으면 어느 쪽도 먼저 만들 수 없다. Spring Boot 2.6부터는 순환 참조를 기본적으로 금지해 기동 시점에 실패한다. 주입 방식을 바꿔 우회하기보다 공통 로직을 별도 클래스로 분리해 구조를 고치는 게 원칙이다.</p><h2>10. 면접 질문으로 정리</h2><ol><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>Q. contenteditable="false"></span><strong>Q. 생성자 주입을 권장하는 이유는?</strong> final로 불변성을 보장하고, 의존성이 누락되면 객체 생성 시점에 바로 실패하며, 스프링 없이도 테스트에서 직접 생성할 수 있고, 순환 참조를 기동 시점에 발견할 수 있기 때문이다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>Q. 스프링 빈은 기본적으로 싱글톤인데 주의할 점은?</strong> 여러 스레드가 같은 인스턴스를 공유하므로 요청마다 바뀌는 상태를 필드에 두면 안 된다. 무상태로 설계해야 한다.</li><li
