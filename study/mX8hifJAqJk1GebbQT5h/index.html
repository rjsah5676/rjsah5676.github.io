스프링 DI: 객체를 직접 만들지 않는다는 것의 의미

Java2026-1-21 22:10

스프링을 쓰면서 new를 거의 쓰지 않게 된다. 서비스가 리포지토리를 필요로 하면 생성자에 적어두기만 하면 스프링이 알아서 넣어준다. 이게 의존성 주입(DI)이고, 객체 생성과 연결의 주도권을 컨테이너에 넘긴다는 점에서 IoC(제어의 역전)라고 부른다.

왜 직접 만들지 않나

// 직접 생성: OrderService가 구현체를 고른다
public class OrderService {
private final PaymentClient client = new TossPaymentClient();
}

이러면 결제사를 바꾸거나 테스트에서 가짜 결제를 넣으려면 OrderService 코드를 고쳐야 한다. OrderService가 "결제를 한다"는 역할뿐 아니라 "어떤 구현을 쓸지"까지 알고 있기 때문이다.

// 주입: 필요한 역할(인터페이스)만 선언
@Service
public class OrderService {
private final PaymentClient client;
public OrderService(PaymentClient client) { this.client = client; }
}

이제 어떤 구현을 넣을지는 설정이 정한다. 테스트에서는 new OrderService(fakeClient)로 끝난다.

빈과 컨테이너

  1. 빈(Bean): 스프링 컨테이너(ApplicationContext)가 생성하고 관리하는 객체.
  2. 등록 방법: @Component(및 @Service, @Repository, @Controller)로 컴포넌트 스캔, 또는 @Configuration 클래스의 @Bean 메서드.
  3. 외부 라이브러리 객체(RestClient, ObjectMapper, DataSource 설정 등)처럼 클래스에 애노테이션을 달 수 없으면 @Bean으로 등록한다.
  4. 기본 스코프는 싱글톤이다. 컨테이너당 하나만 만들어 공유하므로, 빈에 요청별 상태를 필드로 두면 동시 요청끼리 섞인다.

주입 방식 세 가지

  1. 생성자 주입 (권장)
  2. 수정자(setter) 주입: 선택적 의존성에만
  3. 필드 주입(@Autowired private Foo foo;): 테스트에서 넣을 방법이 없고 final을 못 쓴다

생성자가 하나면 @Autowired를 생략해도 된다(Spring 4.3+). 롬복의 @RequiredArgsConstructor와 함께 쓰면 final 필드만 적으면 된다.

@Service
@RequiredArgsConstructor
public class OrderService {
private final OrderMapper orderMapper;
private final PaymentClient paymentClient;
}

생성자 주입의 장점은 의존성이 불변이고, 빠지면 컴파일·기동 시점에 알 수 있고, 생성자 인자가 7~8개로 늘어나면 "이 클래스가 너무 많은 일을 한다"는 신호가 눈에 보인다는 것이다.

같은 타입의 빈이 여러 개일 때

결제 클라이언트가 Toss, 카드사 두 개 있으면 PaymentClient를 주입받는 곳에서 NoUniqueBeanDefinitionException이 난다.

  1. @Primary: 기본으로 쓸 빈 지정
  2. @Qualifier("tossPaymentClient"): 주입받는 쪽에서 이름으로 선택
  3. 파라미터 이름이 빈 이름과 같으면 그걸로 고른다(마지막 수단, 의도가 잘 안 보임)

다중 DataSource 설정에서 빈 이름이 충돌하는 문제도 여기서 생긴다. 같은 이름의 @Bean이 두 개면 Spring Boot는 기본적으로 덮어쓰기를 막고(allow-bean-definition-overriding=false) 기동이 실패한다.

여러 구현을 전부 받기: 전략 패턴

public interface PaymentClient {
PayMethod method();
PayResult pay(PayRequest req);
}

@Service
public class PaymentRouter {
private final Map<PayMethod, PaymentClient> clients;

// 스프링이 PaymentClient 구현 빈을 전부 List로 넣어줌
public PaymentRouter(List<PaymentClient> list) {
this.clients = list.stream()
.collect(Collectors.toMap(PaymentClient::method, c -> c));
}

public PayResult pay(PayRequest req) {
return clients.get(req.method()).pay(req);
}
}

새 결제 수단은 구현 클래스 하나를 추가하면 끝이다. if-else 분기를 고칠 필요가 없다.

순환 참조

A가 B를, B가 A를 생성자로 받으면 둘 다 만들 수 없다. Spring Boot 2.6부터는 순환 참조를 기본으로 금지해서 기동 시점에 실패한다. 필드 주입으로 바꿔서 "해결"하기보다, 공통 로직을 C로 빼거나 이벤트로 끊는 게 맞다. 순환은 대개 책임 분리가 잘못됐다는 신호다.

프록시와 DI

@Transactional, @Async, @Cacheable이 붙은 빈은 실제로 원본이 아니라 프록시가 주입된다. 다른 빈이 메서드를 호출하면 프록시가 트랜잭션 등을 먼저 처리하고 원본을 부른다. 그래서 같은 클래스 안에서 this.method()로 부르면 프록시를 거치지 않아 @Transactional이 동작하지 않는다. DI를 이해하면 이 함정도 같이 이해된다.

정리

  1. DI의 핵심은 "필요한 것을 선언하고, 연결은 컨테이너에 맡긴다".
  2. 생성자 주입 + final을 기본으로.
  3. 같은 타입이 여럿이면 @Primary/@Qualifier, 전부 필요하면 List/Map으로 받는다.
  4. 주입받는 건 원본이 아닐 수 있다(프록시). 이 사실이 AOP 기능의 동작 범위를 정한다.
