모두 이 클래스를 고치게 된다. 책임별로 나눈다.</p><p><strong>OCP</strong>: 결제 수단이 늘 때마다 <code>if (type == TOSS) ... else if (type == CARD)</code>를 고치는 대신, <code>PaymentClient</code> 인터페이스를 두고 구현 클래스를 추가한다. 기존 코드는 수정하지 않는다.</p><p><strong>LSP</strong>: 정사각형이 직사각형을 상속하면 <code>setWidth</code>만 바꿔도 높이가 같이 바뀌어, 직사각형을 기대한 코드가 깨진다. 상속은 "is-a"보다 "부모 자리에 넣어도 약속을 지키는가"로 판단한다.</p><p><strong>ISP</strong>: 하나의 <code>MemberService</code> 인터페이스에 조회·가입·관리자 기능이 다 있으면 조회만 필요한 쪽도 전부에 의존한다. 역할별 인터페이스로 나눈다.</p><p><strong>DIP</strong>: <code>OrderService</code>가 <code>new TossPaymentClient()</code>를 직접 만들지 않고 <code>PaymentClient</code> 인터페이스를 주입받는다. 스프링 DI가 이 원칙을 실천하는 도구다.</p><h2>7. 상속보다 조합 (Composition over Inheritance)</h2><table><tbody><tr><td data-row="row-1"><strong>구분</strong></td><td userId == ...)</code>를 하드코딩하면 권한 규칙이 바뀔 때 모든 곳을 고쳐야 한다. 권한 판단을 하나의 객체(권한 서비스)로 모으면 SRP와 OCP를 동시에 지키게 된다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>전략 패턴</strong>: 배송비 계산 방식(무료, 정액, 지역별)을 인터페이스로 두고 구현을 갈아끼운다. 다형성과 OCP의 가장 흔한 적용이다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>테스트 용이성</strong>: DIP를 지키면 실제 결제 클라이언트 대신 가짜 구현을 넣어 유닛 테스트할 수 있다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>도메인 메서드</strong>: 상태 변경을 setter로 열어두지 않고 <code>cancel()</code>, <code>confirm()</code> 같은 메서드로만 허용하면 잘못된 상태 전이를 객체가 스스로 막는다.</li></ol><h2>9. 면접 질문으로 정리</h2><ol><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>Q. 객체지향의 4대 SOLID를 설명해주세요.</strong> 단일 책임, 개방-폐쇄, 리스코프 치환, 인터페이스 분리, 의존 역전 원칙으로, 변경이 생겨도 영향 범위를 좁히는 설계 원칙이다.</li><li data-list="bullet"><span class="ql-ui" contenteditable="false"></span><strong>Q. 추상 클래스와 인터페이스의 차이는?</strong> 추상 클래스는 상태와 공통 구현을 가질 수 있고 단일 상속만 가능하며, 인터페이스는 역할을 정의하고 다중 구현이 가능하다.</li></ol>9:X
