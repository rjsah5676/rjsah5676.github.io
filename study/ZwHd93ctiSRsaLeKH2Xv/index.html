useMemo, useCallback, React.memo는 언제 효과가 있고 언제 손해인가

Frontend2026-3-26 21:47

React가 느릴 때 제일 먼저 떠오르는 게 useMemo와 useCallback이다. 그런데 아무 데나 감싸면 코드만 복잡해지고 성능은 그대로이거나 오히려 나빠진다. 성능 관련 훅이 각각 무엇을 아껴주는지부터 정리한다.

먼저: React는 언제 다시 렌더링하나

  1. 컴포넌트의 state가 바뀌면 그 컴포넌트와 모든 자식이 다시 렌더링된다. props가 같아도 마찬가지다.
  2. 렌더링은 "함수를 다시 호출해서 JSX를 만든다"는 뜻이고, 실제 DOM 변경은 달라진 부분만 일어난다.
  3. 그래서 대부분의 재렌더링은 싸다. 비싼 건 "무거운 계산" 아니면 "큰 트리 전체 재렌더링"이다.

useMemo: 비싼 계산 결과를 재사용

const visible = useMemo(
() => products.filter((p) => matches(p, filter)).sort(byPrice),
[products, filter]
);

의존성이 그대로면 이전 결과를 돌려준다. 효과가 있는 경우는 두 가지다.

  1. 계산 자체가 비쌀 때. 대략 렌더 중에 1ms 이상 걸리는 수준(수천 개 정렬·필터 등)이다. console.time으로 재보고 판단한다.
  2. 결과 객체·배열의 참조를 유지해야 할 때. 아래 React.memo 자식에게 넘기거나 이펙트 의존성으로 쓸 때다.

반대로 a + b 같은 계산에 쓰면 의존성 비교 비용과 메모리만 늘어난다.

useCallback: 함수 참조를 유지

useCallback(fn, deps)는 useMemo(() => fn, deps)와 같다. 함수를 빠르게 만들어주는 게 아니라 같은 함수 객체를 돌려줄 뿐이다. 그래서 단독으로는 아무 효과가 없고, 그 참조를 비교하는 쪽이 있을 때만 의미가 있다.

  1. React.memo로 감싼 자식의 props로 넘길 때
  2. 다른 훅의 의존성 배열에 들어갈 때
  3. 커스텀 훅이 함수를 반환할 때(쓰는 쪽에서 의존성으로 쓸 수 있으니)

React.memo: props가 같으면 렌더링 건너뛰기

const Row = memo(function Row({ item, onSelect }) {
return <li onClick={() => onSelect(item.id)}>{item.name}</li>;
});

function List({ items }) {
const [selected, setSelected] = useState(null);
// 이게 없으면 List가 렌더될 때마다 새 함수 -> 모든 Row의 memo가 무력화
const onSelect = useCallback((id) => setSelected(id), []);
return items.map((it) => <Row key={it.id} item={it} onSelect={onSelect} />);
}

memo는 props를 얕게 비교한다. 객체·배열·함수 props가 매번 새로 만들어지면 비교는 항상 실패하고 비교 비용만 추가된다. 그래서 memo, useCallback, useMemo는 보통 세트로 써야 효과가 난다.

메모 없이 해결되는 경우가 더 많다

  1. state를 아래로 내리기: 입력창 state가 페이지 최상단에 있으면 타이핑할 때마다 페이지 전체가 렌더된다. 입력창을 별도 컴포넌트로 빼면 그 컴포넌트만 렌더된다.
  2. children으로 넘기기: <Layout>{heavy}</Layout>처럼 받은 JSX는 Layout의 state가 바뀌어도 다시 만들어지지 않는다.
  3. 렌더 중 계산하기: props로 계산할 수 있는 값을 state + useEffect로 동기화하면 렌더가 두 번 일어난다.
  4. key로 초기화하기: 선택한 사용자가 바뀔 때 폼을 비우려고 이펙트를 쓰는 대신 <Form key={userId} />.

급하지 않은 업데이트 미루기: useTransition, useDeferredValue

메모로 줄일 수 없는 무거운 렌더링이면 "급한 것 먼저" 전략을 쓴다.

const [query, setQuery] = useState("");
const deferredQuery = useDeferredValue(query);
// 입력창은 query로 즉시 반영, 무거운 목록은 deferredQuery로 늦게 따라옴
return (
<>
<input value={query} onChange={(e) => setQuery(e.target.value)} />
<Results query={deferredQuery} />
</>
);

Results가 memo로 감싸져 있어야 query가 바뀌는 급한 렌더에서 건너뛸 수 있다. useTransition은 state를 바꾸는 쪽을 감쌀 수 있을 때(startTransition(() => setTab(next))) 쓰고, 진행 중 여부(isPending)를 같이 준다. 둘 다 렌더링을 빠르게 만드는 게 아니라, 렌더링 중에도 입력이 막히지 않게 우선순위를 나눈다.

useRef: 렌더링에 필요 없는 값

타이머 id, 이전 값, 측정 시각처럼 화면에 안 보이는 값을 state에 두면 바꿀 때마다 렌더가 일어난다. 반응속도 테스트를 만들 때 "파란색이 된 시각"을 ref에 둔 이유도 이것이다. 측정값 때문에 렌더가 한 번 더 일어나면 측정 자체가 흔들린다.

React Compiler 이후

React Compiler(2025년 10월 1.0)는 빌드할 때 컴포넌트를 분석해서 메모이제이션을 자동으로 넣는다. 켜두면 손으로 쓰는 useMemo/useCallback은 대부분 필요 없어진다. 다만 이것도 컴포넌트가 순수하고 훅 규칙을 지켜야 적용되고, 지키지 않은 컴포넌트는 최적화 대상에서 빠진다. 결국 "렌더 중에 부수효과 없이"라는 기본이 더 중요해진다.

측정하는 법

  1. React DevTools Profiler에서 "Highlight updates when components render"를 켜고, 무엇이 왜 렌더되는지(Why did this render) 확인한다.
  2. 프로덕션 빌드로 측정한다. 개발 모드는 StrictMode 이중 렌더와 검사 코드 때문에 몇 배 느리다.
  3. 고친 뒤 다시 재서 차이가 없으면 메모를 지운다.

정리

  1. useMemo: 비싼 계산 또는 참조 유지가 필요할 때.
  2. useCallback: 그 함수를 비교하는 쪽(memo, 의존성 배열)이 있을 때만.
  3. memo: 자주 같은 props로 렌더되는 무거운 컴포넌트에. props 참조가 안정적인지 같이 확인.
  4. 그 전에 구조(state 위치, children, key)로 해결되는지 먼저 본다.
