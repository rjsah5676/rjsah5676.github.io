백엔드 유닛 테스트: 무엇을 단위로 보고, 무엇을 가짜로 바꾸나

Backend2026-5-7 22:52

테스트를 처음 쓸 때 가장 많이 하는 실수는 모든 테스트에 @SpringBootTest를 붙이는 것이다. 스프링 컨텍스트 전체를 띄우니 느리고, 실패해도 원인이 어디인지 모른다. 유닛 테스트는 하나의 동작을 외부 의존성 없이, 빠르게 검증하는 테스트다. Spring Boot + JUnit 5 기준으로 정리한다.

테스트의 층

  1. 유닛 테스트: 클래스 하나. 스프링 없이 new로 만들고 의존성은 가짜(mock)로. 수 ms.
  2. 슬라이스 테스트: 한 계층만 스프링으로 띄움. @WebMvcTest(컨트롤러), @DataJpaTest, @MybatisTest(매퍼). 수백 ms~수 초.
  3. 통합 테스트: @SpringBootTest. 실제 DB(Testcontainers 등)까지 붙여 흐름 전체를 확인. 느리지만 진짜에 가깝다.

비즈니스 규칙은 대부분 1번에서, SQL과 매핑은 2번에서, 핵심 시나리오 몇 개만 3번에서 확인하는 피라미드 구조가 유지보수에 좋다.

기본 도구

  1. JUnit 5: @Test, @BeforeEach, @ParameterizedTest, @Nested, @DisplayName
  2. AssertJ: assertThat(x).isEqualTo(y), assertThatThrownBy(...)처럼 읽히는 단언
  3. Mockito: 의존 객체를 가짜로 만들고(@Mock), 동작을 정하고(given/when), 호출을 확인(verify)

예시: 로그인 실패 잠금 규칙

"마지막 성공 이후 연속 5번 실패하면 잠긴다"는 규칙을 테스트한다고 하자.

@ExtendWith(MockitoExtension.class)
class LoginServiceTest {

@Mock LoginHistoryRepository historyRepository;
@Mock AccountRepository accountRepository;
@InjectMocks LoginService loginService;

@Test
@DisplayName("연속 5회 실패하면 계정이 잠긴다")
void lockAfterFiveFailures() {
// given
given(historyRepository.countFailuresSinceLastSuccess("user1")).willReturn(4);

// when
loginService.recordFailure("user1");

// then
verify(accountRepository).lock("user1");
}

@Test
@DisplayName("4회까지는 잠기지 않는다")
void notLockedBeforeLimit() {
given(historyRepository.countFailuresSinceLastSuccess("user1")).willReturn(3);

loginService.recordFailure("user1");

verify(accountRepository, never()).lock(any());
}
}

given-when-then으로 나누면 테스트 이름만 읽어도 규칙이 문서처럼 보인다. 경계값(4회, 5회)을 꼭 넣는다. 버그는 대부분 경계에서 난다.

여러 입력은 파라미터화

@ParameterizedTest
@CsvSource({
"가나다, 9", // UTF-8 한글 3바이트
"abc, 3",
"'', 0"
})
void utf8Bytes(String input, int expected) {
assertThat(ByteUtils.utf8Length(input)).isEqualTo(expected);
}

테스트하기 어려운 코드 = 의존성이 숨어 있는 코드

  1. LocalDateTime.now()를 메서드 안에서 직접 부르면 "자정을 넘긴 주문" 같은 테스트를 쓸 수 없다. Clock을 주입받으면 테스트에서 시간을 고정할 수 있다.
  2. new RestTemplate()을 메서드 안에서 만들면 가짜로 바꿀 수 없다. 생성자 주입으로 받는다.
  3. static 유틸에 외부 호출이 숨어 있으면 mock하기 어렵다.
@Service
public class CouponService {
private final Clock clock;
public CouponService(Clock clock) { this.clock = clock; }

public boolean isExpired(Coupon c) {
return LocalDateTime.now(clock).isAfter(c.getExpiresAt());
}
}

// 테스트
Clock fixed = Clock.fixed(Instant.parse("2026-05-07T15:00:00Z"), ZoneId.of("Asia/Seoul"));
CouponService service = new CouponService(fixed);

테스트를 쓰려고 생성자 주입으로 바꾸다 보면 설계가 같이 좋아진다. 그게 테스트의 숨은 효과다.

Mock을 쓸 때 주의할 점

  1. 구현을 그대로 베끼는 테스트를 피한다. verify로 내부 호출 순서를 하나하나 검사하면 리팩터링할 때마다 테스트가 깨진다. 결과(반환값, 상태 변화, 외부로 나가는 중요한 호출)를 검증한다.
  2. 값 객체나 단순 DTO는 mock하지 말고 진짜를 만든다.
  3. 리포지토리를 mock한 테스트는 SQL이 맞는지 보장하지 않는다. 쿼리는 슬라이스 테스트로 실제 DB에 대고 따로 검증한다.

슬라이스 테스트에서 빈 바꾸기

Spring Boot 3.4부터 @MockBean은 deprecated되고 Spring Framework의 @MockitoBean을 쓴다.

@WebMvcTest(OrderController.class)
class OrderControllerTest {
@Autowired MockMvc mvc;
@MockitoBean OrderService orderService;

@Test
void 없는_주문은_404() throws Exception {
given(orderService.find(1L)).willThrow(new OrderNotFoundException(1L));
mvc.perform(get("/orders/1")).andExpect(status().isNotFound());
}
}

컨트롤러 테스트에서는 서비스 로직이 아니라 요청 매핑, 검증(@Valid), 응답 코드, JSON 형태를 확인한다.

좋은 유닛 테스트의 조건 (FIRST)

  1. Fast: 수백 개가 몇 초 안에 돌아야 자주 돌린다.
  2. Independent: 실행 순서에 의존하지 않는다. 공유 static 상태 금지.
  3. Repeatable: 시간, 랜덤, 네트워크에 따라 결과가 바뀌지 않는다.
  4. Self-validating: 로그를 눈으로 보는 게 아니라 단언으로 성공·실패가 난다.
  5. Timely: 버그를 고칠 때 그 버그를 재현하는 테스트를 먼저 쓴다. 다시 생기지 않는다는 보증이 된다.
