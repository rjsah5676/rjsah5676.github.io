JOIN과 GROUP BY를 같이 쓸 때 숫자가 부풀려지는 이유

Database2025-11-18 21:39

매출 집계 쿼리를 짜다 보면 JOIN과 GROUP BY를 거의 항상 같이 쓴다. 그런데 둘을 같이 쓰면 문법은 맞는데 숫자가 틀린 쿼리가 쉽게 나온다. 주문 도메인 예시로 동작 원리와 함정을 정리한다.

예시 테이블

  1. orders(order_id, member_id, ordered_at, delivery_fee)
  2. order_items(item_id, order_id, product_id, qty, price)
  3. members(member_id, name, grade)

SQL의 논리적 실행 순서

  1. FROM / JOIN / ON: 테이블을 합쳐 행 집합을 만든다
  2. WHERE: 행을 거른다
  3. GROUP BY: 행을 묶는다
  4. HAVING: 묶음을 거른다
  5. SELECT: 보여줄 값을 계산한다
  6. ORDER BY → LIMIT

WHERE에서 SELECT의 별칭을 못 쓰는 이유, 집계 조건은 HAVING에 써야 하는 이유가 이 순서에서 나온다.

JOIN 종류

  1. INNER JOIN: 양쪽에 짝이 있는 행만
  2. LEFT JOIN: 왼쪽은 전부, 오른쪽은 짝이 없으면 NULL
  3. RIGHT JOIN: 반대. 보통 테이블 순서를 바꿔 LEFT로 쓴다
  4. FULL OUTER JOIN: 양쪽 전부. MySQL/MariaDB는 지원하지 않아 LEFT JOIN ... UNION ... RIGHT JOIN으로 흉내 낸다
  5. CROSS JOIN: 모든 조합(카테시안 곱)

함정 1: LEFT JOIN 조건을 WHERE에 쓰면 INNER JOIN이 된다

"이번 달 주문 수를 회원별로, 주문 없는 회원도 0으로" 보고 싶다.

-- 틀림: 주문 없는 회원(o.* = NULL)이 WHERE에서 걸러짐
SELECT m.member_id, COUNT(o.order_id)
FROM members m
LEFT JOIN orders o ON o.member_id = m.member_id
WHERE o.ordered_at >= '2025-11-01'
GROUP BY m.member_id;

-- 맞음: 오른쪽 테이블 조건은 ON에
SELECT m.member_id, COUNT(o.order_id)
FROM members m
LEFT JOIN orders o ON o.member_id = m.member_id
AND o.ordered_at >= '2025-11-01'
GROUP BY m.member_id;

COUNT(*)가 아니라 COUNT(o.order_id)를 쓴 것도 중요하다. COUNT(*)는 NULL로 채워진 행도 1로 센다. COUNT(컬럼)은 NULL을 세지 않는다.

함정 2: 1:N JOIN 후 SUM하면 부모 값이 부풀려진다

"회원별 총 결제 금액 = 상품 금액 + 배송비"를 구한다.

-- 틀림: 상품이 3개인 주문은 배송비가 3번 더해짐
SELECT o.member_id,
SUM(oi.qty * oi.price) + SUM(o.delivery_fee) AS total
FROM orders o
JOIN order_items oi ON oi.order_id = o.order_id
GROUP BY o.member_id;

JOIN하면 주문 1건이 상품 수만큼 행으로 늘어난다(fan-out). 그 상태에서 주문 단위 값(delivery_fee)을 SUM하면 중복으로 더해진다. 해결은 N쪽을 먼저 집계해서 1:1로 만든 뒤 JOIN하는 것이다.

SELECT o.member_id,
SUM(i.items_amount + o.delivery_fee) AS total
FROM orders o
JOIN (
SELECT order_id, SUM(qty * price) AS items_amount
FROM order_items
GROUP BY order_id
) i ON i.order_id = o.order_id
GROUP BY o.member_id;

1:N 테이블을 두 개 이상 붙이면(주문–상품, 주문–쿠폰) 곱으로 늘어나서 더 크게 틀린다. "JOIN 후 행 수가 몇 개인가"를 항상 먼저 생각한다. COUNT(DISTINCT o.order_id)로 개수는 맞출 수 있지만 금액 합계는 DISTINCT로 해결되지 않는다(금액이 같은 다른 주문까지 합쳐버림).

함정 3: GROUP BY에 없는 컬럼을 SELECT하기

SELECT member_id, ordered_at, COUNT(*)
FROM orders
GROUP BY member_id;

ordered_at은 회원별로 여러 값이 있는데 어떤 걸 보여줄지 정해지지 않았다. MySQL 5.7.5 이상은 ONLY_FULL_GROUP_BY가 기본이라 에러가 나지만, MariaDB는 기본으로 켜져 있지 않아 임의의 한 행 값을 그냥 돌려준다. 결과가 우연히 맞아 보여서 더 위험하다. 원하는 게 마지막 주문일이면 MAX(ordered_at)처럼 명시한다.

"회원별 마지막 주문의 상세 정보"처럼 그룹에서 특정 행 전체가 필요하면 GROUP BY보다 윈도 함수가 맞다.

SELECT *
FROM (
SELECT o.*,
ROW_NUMBER() OVER (PARTITION BY member_id ORDER BY ordered_at DESC) AS rn
FROM orders o
) t
WHERE rn = 1;

WHERE와 HAVING

SELECT member_id, SUM(qty * price) AS amount
FROM orders o JOIN order_items oi USING (order_id)
WHERE o.ordered_at >= '2025-11-01' -- 묶기 전에 행을 거름 (인덱스 사용 가능)
GROUP BY member_id
HAVING amount >= 1000000; -- 묶은 뒤 결과를 거름

집계와 상관없는 조건을 HAVING에 쓰면 거를 수 있는 행까지 다 묶은 뒤에 버리니 느리다. 가능한 조건은 WHERE로 내린다.

정리

  1. LEFT JOIN의 오른쪽 테이블 조건은 ON에.
  2. 1:N JOIN 후 부모 쪽 값을 SUM하지 않는다. N쪽을 먼저 집계하고 붙인다.
  3. GROUP BY에 없는 컬럼은 집계 함수로 감싸거나, 행이 필요하면 윈도 함수로.
  4. 쿼리 결과가 맞는지 확신이 없으면 GROUP BY를 빼고 JOIN 결과 행부터 눈으로 본다. 부풀려진 행이 바로 보인다.
