useEffect와 useLayoutEffect, 안전한 레이아웃 이펙트: 실행 시점과 실사용

Frontend2026-3-12 22:31

함수 컴포넌트에는 생명주기 메서드가 없다. 대신 "렌더링 결과가 화면에 반영된 뒤 무엇을 동기화할지"를 이펙트로 선언한다. 이펙트 종류마다 실행 시점이 달라서, 시점을 잘못 고르면 화면이 깜빡이거나 SSR에서 경고가 나고 이벤트 핸들러가 옛날 값을 보게 된다. 실제로 겪은 사례를 기준으로 정리한다.

한 번의 업데이트에서 일어나는 일

  1. Render: 컴포넌트 함수를 호출해서 새 JSX를 만든다. 순수해야 하고, DOM에 손대면 안 된다.
  2. Commit: React가 실제 DOM을 바꾼다. useInsertionEffect는 DOM이 바뀌기 전에, ref 연결과 useLayoutEffect는 바뀐 직후에 동기로 실행된다.
  3. Paint: 브라우저가 화면을 그린다.
  4. Passive effect: useEffect가 실행된다. 보통 paint 이후라서 화면 표시를 막지 않는다.

cleanup은 "다음 이펙트가 실행되기 직전"과 "언마운트될 때" 실행된다. 의존성이 바뀌면 이전 cleanup이 먼저 돌고 새 이펙트가 돈다.

useEffect: 외부 시스템과 동기화

네트워크 요청, 구독, 타이머, 브라우저 API처럼 React 바깥의 무언가와 맞추는 용도다. 렌더 결과로 계산할 수 있는 값을 state에 복사하려고 쓰면 렌더가 한 번 더 일어나니, 그럴 땐 렌더 중에 계산한다.

useEffect(() => {
const controller = new AbortController();
fetch(`/api/orders?page=${page}`, { signal: controller.signal })
.then((r) => r.json())
.then(setOrders)
.catch((e) => {
if (e.name !== "AbortError") setError(e);
});
// page가 빨리 바뀌면 이전 요청을 취소해서 늦게 도착한 응답이 덮어쓰지 않게
return () => controller.abort();
}, [page]);

cleanup에서 요청을 끊지 않으면 1페이지 응답이 2페이지 응답보다 늦게 와서 화면이 거꾸로 바뀌는 경쟁 상태가 생긴다.

useLayoutEffect: 그리기 전에 측정하고 고칠 때

DOM 크기나 위치를 읽어서 그 값으로 다시 배치해야 하면 useLayoutEffect를 쓴다. paint 전에 동기로 실행되므로 사용자는 중간 상태를 보지 못한다.

useLayoutEffect(() => {
const rect = anchorRef.current.getBoundingClientRect();
const tipHeight = tipRef.current.offsetHeight;
// 아래 공간이 부족하면 위로 띄움 - useEffect였다면 한 프레임 아래에 그려졌다가 튐
setPlacement(rect.bottom + tipHeight > window.innerHeight ? "top" : "bottom");
}, [open]);

대신 동기 실행이라 무거운 작업을 넣으면 그만큼 화면 표시가 늦어진다. "깜빡임이 보일 때만" 쓰는 게 원칙이다.

SSR에서 안전한 레이아웃 이펙트

서버에는 DOM도 paint도 없어서 useLayoutEffect가 실행되지 않는다. React 18까지는 서버 렌더 중에 경고까지 출력했다. 그래서 라이브러리들은 환경에 따라 훅을 바꿔 끼우는 패턴을 많이 쓴다. 이름은 useIsomorphicLayoutEffect, useSafeLayoutEffect 등 제각각이지만 내용은 같다.

// 브라우저에선 layout effect, 서버에선 (어차피 실행 안 되는) useEffect
export const useSafeLayoutEffect =
typeof window !== "undefined" ? useLayoutEffect : useEffect;

중요한 건 이 훅이 서버 렌더 결과를 바꿔주지는 않는다는 점이다. 서버 HTML은 측정 전 상태로 나가고, 하이드레이션 직후에 보정된다. 첫 화면부터 맞아야 하는 값이면 CSS로 해결하는 게 낫다.

useInsertionEffect: CSS-in-JS 라이브러리용

DOM 변경 전에 <style> 태그를 넣기 위한 훅이다. 레이아웃 이펙트가 스타일이 적용된 상태에서 측정하도록 보장하는 게 목적이라 애플리케이션 코드에서 쓸 일은 거의 없다. ref도 아직 연결되지 않은 시점이다.

useEffectEvent: 이펙트 안에서 최신 값만 읽고 싶을 때

채팅방 연결 이펙트 안에서 테마 값으로 알림을 띄우면, 테마가 바뀔 때마다 재연결된다. 읽기만 하는 값은 의존성에서 빼고 싶을 때 React 19.2부터 안정화된 useEffectEvent를 쓴다.

const onConnected = useEffectEvent(() => {
showToast(`연결됨`, theme); // 항상 최신 theme을 읽지만 반응하진 않음
});

useEffect(() => {
const conn = connect(roomId);
conn.on("connected", onConnected);
return () => conn.disconnect();
}, [roomId]); // theme이 바뀌어도 재연결 안 함

예전에는 같은 목적을 useRef에 최신 함수를 넣어두는 방식으로 풀었다. 이때 렌더 중에 ref.current = fn을 대입하면 lint(react-hooks/refs)에 걸리므로 이펙트 안에서 갱신한다.

StrictMode의 두 번 실행

개발 모드 StrictMode는 마운트 직후 cleanup → 재실행을 한 번 더 한다. cleanup이 빠진 이펙트를 일부러 드러내려는 것이다. 이 사이트에서도 이 때문에 버그가 난 적이 있다.

// 버그: 첫 이펙트가 기본값을 localStorage에 써버림
useEffect(() => { setSettings(load()); }, []);
useEffect(() => { save(settings); }, [settings]); // 아직 기본값인 settings를 저장

// 수정: 불러오기가 끝난 뒤에만 저장
const [hydrated, setHydrated] = useState(false);
useEffect(() => { setSettings(load()); setHydrated(true); }, []);
useEffect(() => { if (hydrated) save(settings); }, [settings, hydrated]);

두 번 실행돼서 깨지는 코드라면 프로덕션에서도 라우트 전환, Fast Refresh, 향후 Activity(오프스크린) 같은 상황에서 똑같이 깨질 수 있다.

클래스 생명주기와 대응

  1. componentDidMount / componentDidUpdate: 의존성 배열이 있는 이펙트. 실행 시점은 useLayoutEffect에 더 가깝다(동기).
  2. componentWillUnmount: 이펙트의 cleanup.
  3. getSnapshotBeforeUpdate: 대응 훅이 없다. 스크롤 위치 보존 같은 건 useLayoutEffect와 ref로 흉내 낸다.

정리

  1. 기본은 useEffect. 화면이 한 프레임 튀는 게 보일 때만 useLayoutEffect.
  2. SSR이 있는 코드에서 레이아웃 이펙트가 필요하면 safe/isomorphic 패턴으로 감싼다.
  3. 이펙트에서 읽기만 하는 값은 useEffectEvent로 분리해서 의존성을 줄인다.
  4. 이펙트를 쓰기 전에 "이게 외부 시스템과의 동기화인가?"를 먼저 묻는다. 아니면 렌더 중 계산이나 이벤트 핸들러로 옮긴다.
