CI/CD: 커밋에서 배포까지 사람이 하던 일을 파이프라인으로 옮기기

etc2026-6-23 22:16

CI/CD는 도구 이름이 아니라 습관에 가깝다. "main에 합치기 전에 항상 빌드와 테스트가 돈다", "배포는 버튼 하나(또는 머지 하나)로 같은 방식으로 된다". 이 두 가지를 사람이 아니라 자동화가 보장하게 만드는 것이다.

용어

  1. CI (Continuous Integration): 여러 사람의 변경을 자주 합치고, 합칠 때마다 자동으로 빌드·테스트해서 깨진 걸 바로 찾는다.
  2. CD (Continuous Delivery): 언제든 배포 가능한 상태의 결과물을 자동으로 만들어 둔다. 실제 운영 배포는 사람이 승인한다.
  3. CD (Continuous Deployment): 승인 없이 테스트를 통과하면 운영까지 자동으로 나간다.

대부분의 팀은 개발 서버는 자동 배포, 운영은 승인 후 배포(Delivery)로 운영한다.

파이프라인의 기본 단계

  1. 트리거: PR 생성, main 머지, 태그 생성, 수동 실행, 스케줄
  2. 체크아웃 + 의존성 설치: 캐시를 써서 매번 처음부터 받지 않는다
  3. 정적 검사: lint, 포맷, 타입 체크
  4. 테스트: 유닛 → 통합
  5. 빌드: 산출물(jar, 정적 파일, 도커 이미지) 생성
  6. 배포: 환경별로(dev → stage → prod)
  7. 검증·알림: 헬스 체크, 슬랙 알림, 실패 시 롤백

앞 단계가 실패하면 뒤 단계는 돌지 않는다. 빠르고 싼 검사를 앞에 둬서 실패를 빨리 알려주는 게 원칙이다.

GitHub Actions 예시

정적 사이트를 PR마다 미리보기로 올리고, main에 머지하면 운영에 배포하는 구성이다.

name: deploy
on:
push:
branches: [main]
workflow_dispatch: # 수동 실행 버튼

jobs:
build-deploy:
runs-on: ubuntu-latest
steps:
- uses: actions/checkout@v4
- uses: actions/setup-node@v4
with:
node-version-file: .nvmrc
cache: npm # node_modules 다운로드 캐시
- run: npm ci # lock 파일 그대로 설치 (재현 가능)
- run: npm run lint
- run: npm run build
- uses: FirebaseExtended/action-hosting-deploy@v0
with:
repoToken: ${{ secrets.GITHUB_TOKEN }}
firebaseServiceAccount: ${{ secrets.FIREBASE_SERVICE_ACCOUNT }}
channelId: live
  1. npm install이 아니라 npm ci를 쓴다. lock 파일과 다르면 실패하므로 "내 PC에선 되는데"가 줄어든다.
  2. 비밀 값은 저장소 Secrets에 두고 ${{ secrets.X }}로만 참조한다. 로그에는 마스킹된다.
  3. PR용 워크플로는 channelId를 비워두면 PR마다 임시 미리보기 URL이 생긴다. 리뷰어가 실제 화면을 보고 머지할 수 있다.

백엔드라면: 이미지를 만들고, 태그로 배포한다

  1. 테스트 통과 후 docker build로 이미지를 만든다.
  2. 태그는 latest가 아니라 커밋 SHA나 버전으로 붙여 레지스트리에 올린다. 무엇이 배포됐는지 추적되고, 롤백은 이전 태그로 되돌리면 끝이다.
  3. 쿠버네티스라면 Deployment의 이미지 태그를 바꾸고(직접 kubectl set image 또는 매니페스트 저장소를 수정해 ArgoCD 같은 GitOps 도구가 반영), 롤링 업데이트가 진행된다.

배포 전략

  1. 롤링 업데이트: 파드를 하나씩 새 버전으로 교체. 쿠버네티스 기본값. 잠깐 두 버전이 공존하므로 API·DB 변경은 하위 호환으로 나눠서 배포한다.
  2. 블루-그린: 새 환경(그린)을 통째로 띄우고 트래픽을 한 번에 전환. 롤백이 즉시 되지만 자원이 두 배 든다.
  3. 카나리: 트래픽의 일부(예: 5%)만 새 버전으로 보내고 지표를 보며 늘린다.

롤링 업데이트에서는 readiness probe가 중요하다. 애플리케이션이 아직 기동 중인데 트래픽을 받으면 배포할 때마다 에러가 난다. Spring Boot라면 Actuator의 /actuator/health/readiness를 쓴다.

좋은 파이프라인의 조건

  1. 빠르다: 10분 넘게 걸리면 사람들이 기다리지 않고 머지한다. 의존성 캐시, 테스트 병렬화, 변경된 모듈만 빌드.
  2. 재현 가능하다: 같은 커밋이면 같은 결과물. lock 파일, 고정된 런타임 버전(.nvmrc, Gradle toolchain).
  3. 실패가 명확하다: 실패하면 빨갛게 멈춘다. 경고만 찍고 계속 가는 단계가 많으면 아무도 안 본다. 빌드 중 외부 데이터를 가져온다면 "못 가져옴"을 "빈 결과"로 처리하지 않고 빌드를 실패시킨다.
  4. 롤백이 쉽다: 이전 산출물이 남아 있고, 되돌리는 방법이 배포와 같은 버튼이다.

정리

CI는 "합치기 전에 깨진 걸 찾는 자동화", CD는 "배포를 반복 가능한 절차로 만드는 자동화"다. 처음부터 거창할 필요 없이 lint + build만 PR마다 돌려도 효과가 크고, 거기에 테스트, 미리보기, 자동 배포를 하나씩 붙여 가면 된다.
